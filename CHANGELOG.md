## [1.13.1] — 2026-10-02 — Приложение само обновляется: старый SW-кэш больше не подсовывает старый код

### Контекст
«Райдера до сих пор все параметры не сохраняются!!» — при том что код v1.13.0
сохранял уже всё (проверено: store+partialize, riders-sync, bike-storage).
Причина расхождения: **PWA service worker**. После релиза открытая страница
продолжала жить на старом JS: новый SW ставился в очередь, dev-чанки
`/_next/static/*` отдаются кэш-первым из старого кэша, а без
`controllerchange`-перезагрузки пользователь не получал новый код с одного
refresh'а. Пользователь честно тестировал старое поведение (v1.12.0 и ранее —
с багом «сброса всего при перезаходе») и делал вывод «не работает до сих пор».

### Исправлено
- `register-sw.tsx`: `updateViaCache: "none"` — браузер всегда перепроверяет
  sw.js; `reg.update()` на старте — обновление ищется сразу, а не только по
  навигации; при `controllerchange` (новый SW взял управление) страница
  перезагружается **один раз** автоматически.
- Защита от цикла перезагрузок: только если у страницы уже был контроллер
  (реальное обновление, не первый визит) + sessionStorage-флаг, который новая
  страница снимает при загрузке (следующее обновление тоже сможет
  перезагрузить вкладку).

### Версии
- APP_VERSION → v1.13.1, package.json → 1.13.1, SW-кэш `bikesnap-v1.13.1`,
  WHATS_NEW — новая запись сверху.

## [1.13.0] — 2026-10-02 — Прогресс сохраняется всегда: открылись — продолжили

### Исправлено (главная боль)
- **После refresh/перезахода приложение открывается ровно на том же шаге**:
  в `bikefit-storage` теперь хранятся и позиция (`mode`, `step`, `selectStep`),
  и все данные. Раньше сохранялись только цифры — режим сбрасывался на
  стартовый экран, шаг на «Тело».
- **Цель посадки и жалобы больше не стираются при перезаходе**: карточка
  «Настроить мой велосипед» на стартовом экране вызывала `reset()` и
  обнуляла всё; «выживали» только рост/inseam (их восстанавливал sync
  активного райдера) — это и был симптом «цифры сохранены, остальное нет».

### Добавлено
- Стартовый экран: баннер «Продолжить с того места, где остановились» —
  показывается, когда есть незавершённый сценарий, возвращает на
  сохранённый шаг без сброса. Карточки режимов стали честным
  «начать заново» с подсказкой, что прогресс будет удалён.
- «На главную» (логотип, кнопка в подборе рамы) больше не теряет шаг —
  «Продолжить» вернёт ровно туда же.
- Подбор рамы: шаг мастера переехал из локального `useState` в store —
  тоже переживает refresh.
- Hero: «Прогресс сохраняется автоматически — можно вернуться в любой
  момент».

### Техническое
- `partialize` сохраняет `mode`/`step`/`selectStep`; `merge`-санитайзер
  ре-гидрации отбрасывает мусор (напр. `step: "context"` из ≤ v1.11.x,
  `selectStep` вне 0–3) — старые бэкапы совместимы.
- `page.tsx`: mounted-гейт против SSR hydration mismatch (mode известен
  только на клиенте; до маунта — лёгкая заглушка с пульсирующим байком).
- `resetMode()` больше не сбрасывает `step` (только `mode: null`).
- Бейдж режима настройки «5 шагов» → «4 шага» (хвост от шага «Контекст»).

### Версии
- APP_VERSION → v1.13.0, package.json → 1.13.0, SW-кэш `bikesnap-v1.13.0`,
  WHATS_NEW — новая запись сверху (заодно исправлен порядок: 1.12.0
  поднята выше 1.11.1).

- Удалён мёртвый хук `use-onboarding-context.ts` (не использовался).

## [1.11.1] — 2026-10-01 — Защита масштаба от опечаток («SH = 8» больше не ломает математику)

### Контекст
- Кейс из отчёта отладки: в зелёной панели «Калибровка масштаба» поле SH
  содержало «8», а карточка велика — «800». `knownValue` берётся из поля
  калибровки и применяется СТРОГО → масштаб 0.0046 мм/px вместо ~0.46 →
  все метрики ровно в 100 раз меньше (Reach=5, Stack=6, WB=11).
  Причина живучести мусора: синхронизация `calibInputs` ↔ `measured`
  заполняла только ПУСТЫЕ поля — однажды введённое значение не исправлялось
  никогда. Движок доверял любому значению > 0 без проверки на физическую
  возможность.

### Исправлено (три слоя защиты)
- **Синхронизация** (`BikePhotoCalibrator`): при изменении карточки велика
  зеркалим во ВСЕ нетронутые поля калибратора (dirty-tracking через ref —
  осознанный оверрайд пользователя не перетирается).
- **Pre-flight guard в `runCalibration`** (единая точка всех путей расчёта):
  primary-значение вне физического диапазона → фолбэк на значение из
  карточки (с явной строкой 🛡 в логе); если и в карточке мусор — расчёт
  блокируется с понятной ошибкой вместо 100x-нометрики.
- **Ядро** (`bike-geometry-engine`): `OVERRIDE_PHYSICAL_RANGE_MM`
  (SH 400–1000, ETT 300–700, WB 700–1600) + `isPlausibleOverrideMm()`;
  строгий override применяется ТОЛЬКО если значение физически возможно,
  иначе — громкое предупреждение и fallback по колёсной базе (fallback WB
  тоже валидируется). Кросс-чек расхождений считается только для принятого
  override.

### UI
- Мусорное поле: красная рамка + подсказка «N мм — вне физического
  диапазона X–Y. Поле не допускается до масштаба»; авто-исправление onBlur
  из карточки (или очистка) с записью в лог.
- Расхождение поля с карточкой (оба валидны): жёлтая плашка
  «ⓘ В карточке велика: N мм — масштаб строго по этому полю».
- Red banner над статусом, когда primary вне диапазона.
- В логе: отдельные строки 🛡 (мусор заменён/блокировка) и
  ⓘ «Поле калибровки (N) ≠ карточка (M)».

### Версии
- APP_VERSION → v1.11.1, package.json → 1.11.1, SW-кэш `bikesnap-v1.11.1`,
  WHATS_NEW — новая запись сверху.

## [1.8.0] — 2026-10-01 — PWA: установка на рабочий стол телефона и ПК

### Добавлено
- **Web App Manifest** (`public/manifest.webmanifest`): standalone-режим
  (без адресной строки), `orientation: any` — ландшафтная фото-съёмка

  тёмный скруглённый квадрат + белая пиктограмма велосипеда с изумрудными

- **Метаданные**: `manifest`, `appleWebApp` (capable, black-translucent),
  `themeColor #121214`, `viewport-fit: cover` (безопасные зоны iPhone),

## [1.7.0] — 2026-10-01 — Детектор колёс v2: лучевое голосование вместо бинаризации

### Проблема (от пользователя)
«Объектив очень плохо работает, точнее совсем не работает… он вообще колес
не видит, а если и видит то криво».

### Почему v1 не работал (разбор)
- Глобальный порог Отсу смешивал асфальт, тени, раму и покрышки в одно пятно →
  гигантская связная компонента отбрасывалась фильтром площади → «колёс не видно».
- Когда маска распадалась удачно, эллипс по моментам натягивался на мусор
  (тень, нога, столб) → «видит, но криво».
- На синтетике v1-тесты были слепы к размеру: детектор находил ВНУТРЕННЮЮ
  границу покрышки (кольцо радиусом 0.62R) и честно отдавал «круг» вдвое
  меньше колеса — оверлей рисовал окружности не вокруг колёс.

### Детектор v2 (`src/lib/wheel-detect.ts`, полный реворк)
- Собель-градиенты вместо порога «темноты»: локальные перепады работают на
  любом фоне и при любом освещении.
- ЛУЧЕВОЕ голосование: каждый краевой пиксель рисует луч вдоль градиента через
  все расстояния; центр колеса собирает O(периметр) голосов, случайные
  пересечения (текстура, прямые края) — O(1). Контраст 50:1 к шуму.
- АСПЕКТ-ПРОХОДЫ k ∈ {1.0, 1.4, 1.9} (центро-сохраняющее растяжение по X):
  овал с сжатием 1/k в своём проходе — круг с одним чистым пиком. Лечит
  «куспы» эволюты (нормали наклонного эллипса проходят мимо центра и дают
  4 ложных пика сверху/снизу).
- Уточнение: радиальный профиль → мультипликативная сетка формы → координатный
  спуск центр ↔ форма (3 раунда, шаг 3→2→1.5).
- Верификация: покрытие эллипса краями ≥ 50% с радиальным направлением
  градиента + мягкий контраст «кольцо темнее соседей» (дисковое колесо
  не отсекает) + гейты размера/сжатия.
- Отладочный хук `detectWheels(img, debug?)` — пул/уточнённые/принятые

- Производительность: ~20 мс на кадр 320px (в Web Worker, цикл 280 мс —

  неизменны); внутренняя согласованность ETT = Reach + Stack/tan(STA);
  валидация вырожденных/инвертированных точек.
- Значения в выровненной системе отличаются от старого лога на ≈2° наклона:
  Reach 430→410, Stack 594→608, STA 72.9→70.9 — это эффект применения

## [Unreleased.3] — 2026-09-29 — CRITICAL: Fix scale units mismatch (626032 → 626 mm)

### Исправлено (КРИТИЧЕСКИЙ БАГ)
- **SH = 626032 мм вместо ~626 мм** — масштаб был завышен в ~1000 раз.
- **Причина**: `computeRigorousBikeParams` использовал `toPx()` для конвертации нормализованных [0..1] координат в пиксели, но `scale` из `calibrateScale` был в **мм/норм.ед.** (не мм/пиксель).
- Результат: `пиксели × (мм/норм.ед.) = норм.ед. × imgSize × мм/норм.ед. = мм × imgSize` ← перебор ~1200x.
- **Решение**: переписал `computeRigorousBikeParams` — теперь работает с **нормализованными** координатами [0..1] напрямую (без `toPx()`).
  - `normDist(a, b)` — Евклидово расстояние в норм.ед.
  - `normH(a, b)` — горизонталь в норм.ед.
  - `normV(a, b)` — вертикаль в норм.ед.
  - `normPerp(p, lineA, lineB)` — перпендикуляр в норм.ед.
  - `pxDist = normDist × safeScale = норм.ед. × (мм/норм.ед.) = мм` ✓
- Углы STA/HTA не пострадали (atan2 масштабо-независим), но `_imgSize` теперь неиспользуется (помечен как `_`).
- Параметр `imgSize` в `computeParamsFromPhoto` по-прежнему нужен (передаётся для проверки и future use).
